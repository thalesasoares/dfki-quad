## 1. What the issue asks

Centralize "adaptation updated model → push to all stages" so new plugins opt in via interface
instead of the host hardcoding the per-stage `UpdateModel` calls. Acceptance criteria:

1. Single broadcast/helper path from host after model adaptation update.
2. Stages opt in via interface method (**existing** or extended).
3. Adding a new stage does not require editing a hardcoded list of calls in multiple places (or the
   list is data-driven).
4. No behavior change for KF/RLS adaptation defaults (`model_adaptation.type` =
   `kf_adaptation` / `rls_adaptation`, `plugins/model_adaptation_plugins.xml:18,23`).

The issue text says "four `UpdateModel` calls"; since M3.1 there are **five** — the contact stage
joined the fan-out (`mit_controller_node.cpp:879`). The docs already assign this exact code to #15:

- `stage_contracts.md` §4.5: "the model-update fan-out that issue #15 (M3.4) will factor into a
  helper" (line ~301) and §5: "The model-update broadcast … is duplicated logic across four stages
  and is issue #15 (M3.4)" (line ~498).
- `pipeline_host.md` §8 (line ~183-192): the G6/G10 lock-discipline gaps "overlap the code …
  #15 (M3.4) reworks (the model update broadcast), **which is where the locking wants to be decided
  once**. They should be a change of their own, on top of this one."

### Long-term context (why the shape below, not just a smaller diff)

- **M4.1/M4.2** add selectable/example plugins behind the *existing* five interfaces — they inherit
  `UpdateModel` and are covered automatically, because the broadcast registers host *slots*
  (`mpc_`, `gs_`, …), not concrete types.
- **M4.3** (contributor guide) needs one documented sentence for model updates: "implement
  `UpdateModel` (it's on every stage interface) and add one `Register` line at bring-up." The helper
  is that single site.
- **G6** (gs updated under `mpc_lock_`, model mutated unlocked — `stage_contracts.md` §7) stays
  open by design here, but after this change fixing it is a one-argument edit at one registration
  line instead of a loop-body surgery. That is the "locking decided once" place §8 asks for.

## 3. Design decisions (settled — do not re-open)

**D1 — Opt-in is the *existing* `UpdateModel` method. No new common base interface.**
All five stage interfaces already declare `void UpdateModel(const ModelInterface&)` with identical
semantics (`stage_contracts.md` §4 tables). Introducing a shared `ModelUpdateReceiver` base that the
five interfaces inherit was rejected: it edits all five frozen M1.1 headers, changes every shipped
plugin's vtable/ABI for zero functional gain, and the contract tests pin the method tables as they
are. The acceptance text explicitly allows "existing". What *is* centralized is the host-side call
list, which becomes data (D2).

**D2 — A host-owned registry: `ModelUpdateBroadcast`, header-only, in
`include/model_update_broadcast.hpp`.**

```cpp
// Host-side fan-out for the model-adaptation broadcast (issue #15, M3.4).
// Not part of the exported plugin surface: a stage author only implements
// UpdateModel; *this* is how the host remembers whom to call and under which
// lock. See doc/modularity/model_update_broadcast.md.
class ModelUpdateBroadcast {
 public:
  ModelUpdateBroadcast() = default;
  // Entries capture references to host members (locks and stage slots);
  // copying would silently rebind nothing. Non-copyable, like StageLoader.
  ModelUpdateBroadcast(const ModelUpdateBroadcast&) = delete;
  ModelUpdateBroadcast& operator=(const ModelUpdateBroadcast&) = delete;

  // Registers a stage slot under the mutex its UpdateModel runs under today.
  // `slot` is the host's member PluginPtr taken BY REFERENCE — the entry
  // dereferences it at broadcast time, so a runtime stage swap (the gait
  // sequencer reload, mit_controller_node.cpp:486-502) is picked up
  // automatically and the registry never holds a dangling stage pointer.
  // Registration order is broadcast order. Bring-up only, never on a loop.
  template <class StagePtr>
  void Register(std::string name, std::mutex& lock, const StagePtr& slot) {
    entries_.push_back(
        {std::move(name), &lock, [&slot](const ModelInterface& m) { slot->UpdateModel(m); }});
  }

  // Fans the model out in registration order. Consecutive entries sharing a
  // mutex run under ONE lock acquisition and are reported in ONE
  // "Updated used Model in <names joined with ' and '>" INFO line — the exact
  // grouping, lock count and log text of the hardcoded list this replaces.
  void Broadcast(const ModelInterface& model, const rclcpp::Logger& logger) const;

 private:
  struct Entry {
    std::string name;
    std::mutex* lock;
    std::function<void(const ModelInterface&)> update;
  };
  std::vector<Entry> entries_;
};
```

`Broadcast` implementation: walk `entries_` with an index; for each run of consecutive entries whose
`lock` pointer is equal, take one `std::lock_guard`, call each `update(model)`, release, then emit
one `RCLCPP_INFO(logger, "Updated used Model in %s", joined_names)`. No allocation besides the
joined name string, which happens only on the rare model-changed event right next to an existing
`RCLCPP_INFO` (§6). A `std::function` per entry (bound once at bring-up) was chosen over a common
base pointer (rejected in D1) and over a template-heavy tuple design — five type-erased calls per
*event* is nanoseconds, and the entry list stays a plain runtime vector, which is what "data-driven"
means here.

**D3 — Host wiring.**
- `mit_controller_node.hpp`: add `#include "model_update_broadcast.hpp"` and one member,
  `ModelUpdateBroadcast model_update_broadcast_;`, declared **after** the stage pointers (its
  entries reference the locks and the `PluginPtr` slots; it never runs during teardown, but keeping
  it below the members it references is the same hygiene the loader/pointer ordering comment
  `:121-126` establishes).
- Registration block in the constructor, immediately after the "Pipeline stages loaded" INFO
  (`:553-561`) — all six stages exist by then, no loop has started:

```cpp
// The model-update broadcast (issue #15, M3.4). Registration order and lock
// grouping reproduce the hardcoded fan-out this replaces byte-for-byte:
// MPC and GS under mpc_lock_ (GS deliberately NOT under gait_sequencer_lock_ —
// gap G6, stage_contracts.md §7, still open and still a separate change),
// WBC and the contact stage under wbc_lock_, SLC under slc_lock_. Adding a
// stage to the pipeline means adding ONE line here — nothing else.
model_update_broadcast_.Register("MPC", mpc_lock_, mpc_);
model_update_broadcast_.Register("GS", mpc_lock_, gs_);
model_update_broadcast_.Register("WBC", wbc_lock_, wbc_);
model_update_broadcast_.Register("contact logic", wbc_lock_, contact_logic_);
model_update_broadcast_.Register("SLC", slc_lock_, slc_);
```

- `ModelAdaptationCallback` (`:867-885`): keep `:867-869` (the `changed_model` guard, the
  "Model Adaptation changed QuadModel" INFO, the msg declaration); replace `:870-885` (three
  lock/unlock pairs, five calls, three INFOs) with

```cpp
model_update_broadcast_.Broadcast(quad_model_, this->get_logger());
```

  Everything after — the `/quad_model` publish `:886-890`, its INFO `:891`, the heartbeat counter
  `:892-894` — stays exactly where it is. The stage names above reproduce the current log lines
  byte-for-byte: "Updated used Model in MPC and GS", "… in WBC and contact logic", "… in SLC".

**D4 — Lock discipline is *unchanged*; G6/G10 stay open, and out of scope.**
`pipeline_host.md` §8 is explicit that the lock fix "should be a change of their own, on top of
this one", and the issue's criterion 4 demands no behavior change. So: GS stays under `mpc_lock_`
(with the comment above naming it deliberate), `quad_model_` stays mutated without its own lock,
sequence and count of acquisitions are identical (three, in the same order → identical contention
and deadlock profile; locks are taken strictly sequentially, never nested — same as today). The
payoff is that the *future* G6 fix becomes editing `mpc_lock_` → `gait_sequencer_lock_` in one
`Register` line.

**D5 — The MA stage is the producer, never a subscriber.** `ma_` is not registered. A future
seventh stage opts in by (a) having `UpdateModel` on its interface — all current interfaces do —
and (b) one `Register` line. Document both halves in the new doc (§5) for M4.3 to link.

**D6 — Header placement keeps the exported plugin surface untouched.**
`include/model_update_broadcast.hpp` sits next to `stage_selection.hpp` (host-internal), NOT in
`include/mit_controller/` (the exported stage/plugin surface of M2.1). No plugin ever includes it.
Consequently no `plugins/*.xml`, no `pipeline_types_surface_check`, and no install/export CMake
change. Includes needed: `<functional> <mutex> <string> <vector>`, `rclcpp/logging.hpp` +
`rclcpp/logger.hpp`, `common/model_interface.hpp`.

**D7 — Behavior-identity checklist (review against this).**
- `use_model_adaptation == false` → nothing changes (guard untouched).
- `changed_model == false` → nothing changes (guard untouched).
- On a model change: same three lock acquisitions in the same order; same five `UpdateModel` calls
  in the same order; same four INFO lines with identical text; `/quad_model` published after the
  broadcast, as today; heartbeat counter unchanged.
- `grep -n "UpdateModel" ws/src/controllers/src/mit_controller_node.cpp` after the change must show
  **zero** direct stage calls — only the `Register`/`Broadcast` machinery.

## 4. Tests

New pure-gtest suite `test/test_model_update_broadcast.cpp`, registered in `CMakeLists.txt` by
cloning the `test_default_contact_logic` stanza (`:131-138`: `PRIVATE include`, deps
`common interfaces rclcpp Eigen3`, `-Wall -Wextra -Wpedantic -Werror`). No ROS init needed —
`rclcpp::get_logger("test")` works without `rclcpp::init`. Use small local fakes (a struct with an
`UpdateModel` that appends to a shared event log) rather than touching `test/fake_stages.hpp`,
which is contract-test infrastructure. A minimal `ModelInterface` fake already exists there if one
is needed for the reference — but the helper only passes the reference through, so a forward-declared
dummy implementing nothing beyond construction is enough (reuse whatever `fake_stages.hpp` provides
if it is cheap; do not extend it).

Cases:
1. **Order** — three entries, two mutexes; `Broadcast` calls `UpdateModel` in registration order,
   each exactly once, with the same model reference.
2. **Under the lock** — an entry whose fake `UpdateModel` does `EXPECT_FALSE(mutex.try_lock())` on
   its registered mutex: proves the call runs with the lock held.
3. **Grouping** — two consecutive entries on mutex A, then one on mutex B: while an A-entry runs,
   `try_lock` on B succeeds (and is unlocked again) — proves locks are per-group, not global; both
   A-entries execute under the same acquisition (observable: the first A-fake locks-then-unlocks
   nothing but sets a flag; the second A-fake asserts A is still held via `try_lock` failure).
4. **Swap tolerance** — register a `std::unique_ptr<Fake>` slot, `Broadcast`, then
   `slot = std::make_unique<Fake>(...)` (or `.swap`) and `Broadcast` again: the second call reaches
   the *new* instance. This pins the capture-by-slot-reference rule that the runtime GS reload
   (`:486-502`) depends on.
5. **Empty registry** — `Broadcast` on a never-registered helper is a no-op (no log, no crash).

Existing suites must stay green (they are the no-regression net for the frozen interfaces and the
host): `test_stage_contracts`, `test_default_contact_logic`, `test_plugin_discovery`,
`test_stage_loader`, `test_stock_plugins`, `test_stage_selection`, `test_go2_yaml_stage_selection`.
None of them touch `ModelAdaptationCallback`, so none should change.

## 6. Performance (explicit no-loss argument — put this in the PR body)

- The touched code path is **event-driven**: it executes only when `DoModelAdaptation` returns
  `true` (a logged, rare event — an actual model change), inside the model-adaptation callback
  group. The 3 control loops (`MPCLoopCallback`, `SLCLoopCallback`, `ControlLoopCallback`) are
  untouched — zero added work at loop rates.
- Identical synchronization: three mutex acquisitions per event, same mutexes, same order, taken
  sequentially and never nested — contention and deadlock profile is unchanged by construction.
- Per event, the five direct virtual calls become five `std::function` invocations (one extra
  indirection + one `unique_ptr` deref each): nanoseconds, against `UpdateModel` bodies that copy
  Pinocchio models / re-seed solvers (µs–ms). Unmeasurable.
- The registry is built once at bring-up; `Broadcast` performs no allocation beyond the joined
  log-label string, emitted alongside a pre-existing `RCLCPP_INFO` on the same rare event.
- Nothing on the exported surface, no new library, no CMake target change → no build-time or
  binary-size effect worth mentioning.

## 7. Out of scope / risks

- **Out of scope**: fixing G6/G10 (lock discipline, unsynchronised diagnostic reads) — explicitly a
  follow-up per `pipeline_host.md` §8; reordering or merging lock groups; registering `ma_`;
  touching the five frozen interfaces; the `SetParameter` routing ladder (`:392-476`), which is a
  *different* hardcoded list with its own future.
- **Risk — dangling captures**: entries reference host members. Mitigated by non-copyability, the
  member declaration position, and the fact that `Broadcast` only runs from a timer that dies with
  the node. Called out in the header comment.
- **Risk — log-text drift**: two INFO strings are load-bearing for "no behavior change" review
  optics; the names in D3 reproduce them exactly. Diff the sim logs before/after (test plan §9).
- **Risk — stale base**: branching from the stale local `feature/modularization_central` (M3.1 tip)
  would silently revert M3.2. §0 first step exists for this reason.
- M3.3 (#14) closed with no merged PR (optional seam, resolved without code) — nothing to rebase
  around.
