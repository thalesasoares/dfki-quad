## 1. What the issue asks

Replace the `USE_WBC` compile fork for the Go2 path with a runtime profile so ArcOPT vs Inverse
Dynamics is a plugin choice, not a rebuild. Acceptance criteria:

1. Go2 can select the WBC plugin at launch/config without rebuilding for that choice.
2. Command output path works for joint and Cartesian modes used by Go2.
3. Documented limitation (if any) for ULab.
4. Stock Go2 sim still walks.

This issue **owns gap G8** (`doc/modularity/stage_contracts.md` §5): `WBCInterface` is a class
template, and a class template cannot be a pluginlib base. Every doc that mentions #13 promises the
same three things — de-template `WBCInterface`, collapse the two WBC plugin bases into one, and
rework **only** `wbc_plugins.xml` among the discovery XMLs. Deliver exactly those.

### The crucial enabler (why this is smaller than it looks)

`libwbc_plugins` is built **unconditionally and robot-agnostically** — both `WBCArcOPT` and
`InverseDynamics` are already compiled into every build (`CMakeLists.txt:522-547`). Only
`mitcontrollernode` gets `ROBOT_MODEL` (`CMakeLists.txt:420-423`), and the fork it drives is purely
host-side typing: the `WBCType` `std::conditional` typedef + `WBC_PLUGIN_BASE` selector
(`mit_controller_node.hpp:120-124`) and the `if constexpr` dispatch lambda
(`mit_controller_node.cpp:1002-1058`). No build-system change is needed to make both WBCs available
at runtime — the work is de-templating the interface and deleting the host's compile-time choice.

## 3. Design decisions (settled — do not re-open)

**D1 — De-template `WBCInterface`: two explicit getters + a mode query (no variant).**
This is the direction already ratified in `stage_contracts.md` §6 change (2). The six `Update*`
methods and `SetParameter` are already type-independent — they move over verbatim. The template's
only real dependency is `GetJointCommand(JointCommandType&)`. Replace with:

```cpp
enum class WBCCommandMode { kJoint, kCartesian };

// Which command family this WBC produces. Fixed for the lifetime of the
// instance; the host reads it once at bring-up and validates it against
// leg_control_mode (§D3). Never called from the control loops.
virtual WBCCommandMode SupportedCommandMode() const = 0;

// Exactly one of the two is the implementation's real solve path, per
// SupportedCommandMode(). The other MUST return {false, 0.0, 0.0} without
// touching the out-param; the host never calls it (bring-up validation), so
// the stub is defence in depth, not a code path.
virtual WBCReturn GetJointCommand(JointTorqueVelocityPositionCommands& joint_command) = 0;
virtual WBCReturn GetCartesianCommand(CartesianCommands& cartesian_command) = 0;
```

Both getters stay **pure virtual** (matching the all-pure style of every stage interface, and so the
contract test can pin both signatures); the unsupported one is a two-line stub in each
implementation. A `std::variant` return was rejected: it buys nothing here (the host already knows
which family it needs from `leg_control_mode`), adds visitation cost/complexity on a 500 Hz path,
and breaks the existing out-param + `WBCReturn` timing convention.

`JointTorqueCommands` (`joint_commands.hpp:16-18`) stays as an exported data struct (it's part of
the M2.1 surface) but ceases to be an interface instantiation — its only "user" was the dead third
template instantiation pinned in `test_stage_contracts.cpp:80,117` and the alias spelling in
`wbc_arc_opt.cpp:214,227`.

**D2 — Unify the `FootContact`/`Wrenches` aliases with the contact stage (promised by
`contract_tests.md:39`).** Once `WBCInterface` is non-template, its member aliases are no longer
per-instantiation. Keep the aliases as member typedefs on both interfaces (call-site spelling
unchanged) but define both from the same underlying types so they cannot drift:
`std::array<bool, ModelInterface::N_LEGS>` / `std::array<Eigen::Vector3d, ModelInterface::N_LEGS>`.
Do **not** make `wbc_interface.hpp` include `contact_logic_interface.hpp` (no cross-stage include
coupling); keep the existing `static_assert(std::is_same_v<…>)` pins in `test_stage_contracts.cpp:124-129`
as the enforcement, and update their comment from "duplicated because template (issue #13)" to
"duplicated deliberately, layout pinned here". This satisfies "unifies them" without inventing a new
exported header for two aliases. (If the implementer finds a natural existing shared header — e.g.
alongside `FeetTargets` — moving the aliases there is an acceptable stretch, but it is not required
and must not grow the exported surface.)

**D3 — Host: one loader, bring-up validation, runtime dispatch.**
- Delete `WBCType`, `WBC_PLUGIN_BASE`, the `std::conditional` include-site comment block
  (`mit_controller_node.hpp:113-124`). `StageLoader<WBCInterface> wbc_loader_{stage_plugin_bases::kWBC};`
  `StageLoader<WBCInterface>::PluginPtr wbc_;`
- **Bring-up validation (fail fast, once):** immediately after
  `wbc_ = wbc_loader_.Load(...)` (`mit_controller_node.cpp:548`), map `leg_control_mode_` to the
  required `WBCCommandMode` (`JOINT_TORQUE_CONTROL`/`JOINT_CONTROL` → `kJoint`;
  `CARTESIAN_JOINT_CONTROL`/`CARTESIAN_STIFFNESS_CONTROL` → `kCartesian`) and compare with
  `wbc_->SupportedCommandMode()`. On mismatch, throw with a message naming **both** parameter values
  and the fix (same fail-fast philosophy as `StageLoader`'s unknown-type error,
  `stage_loading.md` §1). Put the mapping in a small free function (e.g. in `stage_selection.hpp`
  or a host header) so it is unit-testable without a node.
- **Dispatch:** `solve_and_publish` (`mit_controller_node.cpp:1011-1058`) loses the generic-lambda
  `if constexpr` wrapper and becomes a plain switch on `leg_control_mode_` — the Cartesian cases
  call `wbc_->GetCartesianCommand`, the joint cases `wbc_->GetJointCommand`, message `assign(...)`
  and publish exactly as today. The `default:` mismatch branches become unreachable
  (bring-up validation) — keep a defensive `RCLCPP_ERROR` + `return {false,0,0}` rather than UB.
  Update the big comment block at :1002-1010 (it narrates the compile-time story).
- Publisher creation at `mit_controller_node.cpp:217-229` already switches on `leg_control_mode_`
  at runtime — unchanged.

**D4 — Single pluginlib base.** `stage_loader.hpp:71` becomes
`inline constexpr char kWBC[] = "StagePlugin<WBCInterface>";` — delete `kWBCCartesian` (:77) and its
doc comment. `wbc_plugins.xml`: both `wbc_arc_opt` and `inverse_dynamics` declare
`base_class_type="StagePlugin&lt;WBCInterface&gt;"`; rewrite the header comment (it currently
narrates gap G8 and names this PR as the one that reworks it). `wbc_plugins.cpp`: both
`PLUGINLIB_EXPORT_CLASS(..., StagePlugin<WBCInterface>)`. No other XML changes — that isolation is a
documented promise (`plugin_discovery.md:101`).

**D5 — `USE_WBC` survives only as the `wbc.type` default derivation (the documented ULab
transitional path, AC3).** Keep `mit_controller_node.cpp:325`
`declare_parameter(kWBCTypeKey, WBCTypeForBuild(USE_WBC))` and `mit_controller_params.hpp:26-32`
as-is. Rationale: the issue explicitly allows a transitional ULab path; the ULab configs carry no
`wbc.type` key and select through this declared default; and `stage_selection.hpp`'s legacy-bridge
table already documents `wbc.type`'s default as derived from the build flavour, deleted by #23
(M5.4). What changes in meaning — and must be re-documented in `stage_selection.hpp:144-152` and
`mit_controller_params.hpp` — is that after this PR `USE_WBC` **no longer selects any code path**;
it only picks a default *string*. An explicit `wbc.type` in YAML always wins, on any build. That
sentence is the "documented limitation for ULab": a ULab launch that sets no `wbc.type` still gets
`inverse_dynamics` from the build flavour; #23 deletes the derivation and ULab configs then must pin
the key like Go2's already do.

**D6 — Shipped-config consistency; the `mit_controller_sim_ulab.yaml` oddity.**
`mit_controller_sim_ulab.yaml:4` sets `leg_control_mode: 0` (joint) while an ULab build derives
`inverse_dynamics` (Cartesian). Today that combination starts and then errors every control cycle
publishing nothing (`mit_controller_node.cpp:1049-1054`); under D3 it becomes a clean bring-up
failure. That is the *intended* hardening — do **not** weaken the validation for it. Handle the
config: set `leg_control_mode: 3` in `mit_controller_sim_ulab.yaml` so the shipped ULab sim config
is self-consistent (mirroring `mit_controller_real_ulab.yaml:4`), and flag this prominently in the
PR changelog for maintainer confirmation (ULab cannot be regression-run; the alternative reading —
that this file was only ever used with a rebuilt Go2-flavour binary — is exactly the rebuild
workflow this issue removes, and the file keeps both `wbc.arc_opt.*` and `wbc.inverse_dynamics.*`
sections so either plugin remains selectable there by pinning `wbc.type`). Go2 YAML comment at
`mit_controller_{sim,real}_go2.yaml` (`wbc.type` line) changes from
"wbc_arc_opt (go2 build) | inverse_dynamics (ulab build)" to describing the runtime pairing rule:
`wbc_arc_opt` (joint commands — needs `leg_control_mode` 0/1) | `inverse_dynamics` (Cartesian —
needs `leg_control_mode` 2/3).

**D7 — `wbc.type` stays a bring-up-only choice.** No hot-swap of a running WBC (only `gs.type` has
that special case, by design — `mit_controller_node.cpp:385-391`). A runtime set of `wbc.type`
falls into the `wbc.*` router branch (:429-434), reaches `SetParameter`, is refused, and warns —
same behaviour `contact_logic.type` already has (:392-401). Acceptable and consistent; just make
sure both stock adapters' `SetParameter` return `false` for `wbc.type` (they will, by not
recognising it). No new code.

**D8 — No behaviour change on the stock Go2 path.** With `wbc.type: wbc_arc_opt` +
`leg_control_mode: 0` (the shipped Go2 configs), the loaded class, its `Init` parameters, the
per-cycle call sequence (`UpdateState → UpdateTarget → UpdateFeetTarget → UpdateFootContact →
UpdateWrenches → GetJointCommand`), the published `JointCmd`, and all diagnostics are bit-for-bit
the same pipeline as before — only the dispatch plumbing changed. State this in the PR and prove it
with the regression run (§7).

## 6. Performance (a stated requirement — prove no loss)

The design adds **zero** work to the 500 Hz control loop:

| | Before | After |
|---|---|---|
| Command solve | 1 virtual `GetJointCommand` | 1 virtual `GetJointCommand` *or* `GetCartesianCommand` — same vtable-call cost |
| Mode dispatch | `switch (leg_control_mode_)` inside an `if constexpr`-pruned lambda | the same `switch (leg_control_mode_)`, no lambda template |
| Allocation | none (fixed-size POD out-params on the stack) | identical structs, unchanged |
| Mode/type checks | per-cycle logged-error fallback branch | **moved to bring-up** (`SupportedCommandMode` called once); loop keeps only the unreachable defensive branch |
| Plugin load | pluginlib dlopen at startup | unchanged (base string differs, mechanism identical) |

No `std::variant`/`std::any`/`std::function` anywhere on the hot path. `SupportedCommandMode` must
not be called from any loop callback. Empirical check in the human test plan (§7): compare
`/wbc_solve_time` (`PUBLISH_WBC_SOLVE_TIME` is already on) before/after on the stock Go2 sim —
distributions must be statistically indistinguishable; also confirm no new loop-overrun warnings.

## 9. Long-term alignment (why these choices, vs the roadmap)

- **M3 exit criterion** "Go2 WBC selectable at launch" is this PR, verbatim (steps 6-7 of §7.1).
- **M4.2/M4.3** (example plugin, contributor guide): a single non-template WBC base makes "write a
  WBC plugin" documentable like every other stage — the guide can say "implement your mode's getter,
  stub the other, declare `SupportedCommandMode`". Pure-virtual getters keep that contract explicit.
- **M4.4** (launch overlay swapping one stage) gets `wbc.type` for free once it is runtime.
- **#23 (M5.4)** deletes `USE_WBC`, `WBCTypeForBuild`, and the legacy derivations — D5 deliberately
  leaves all of that concentrated in `stage_selection.hpp` + one `declare_parameter` line +
  `mit_controller_params.hpp`, so #23 stays a deletion, not a redesign. After this PR, `ROBOT_MODEL`
  on `mitcontrollernode` exists *only* to feed that default.
- The **Kennel Console** spec (`doc/prompts/kennel_console_ui_spec.md`) composes pipelines from
  config — runtime `wbc.type` is a prerequisite it can now rely on.

## 10. Risks / gotchas checklist for the implementer

- **Base-string change is a breaking change for out-of-tree WBC plugin XMLs** (none exist in-tree).
  Say so in the PR changelog; `stage_loading.md:263` already predicted it.
- `StageLoader` member-declaration order (loaders before plugin pointers,
  `mit_controller_node.hpp:126-137`) must be preserved when editing the members — the dangling-vtable
  comment explains why.
- The `static WBCReturn wbc_return;` and `static double wbc_solve_time` locals in
  `ControlLoopCallback` — leave them as-is (pre-existing; not this PR's cleanup).
- `wbc_arc_opt.cpp` needs `-fpermissive` and header-only fmt (`CMakeLists.txt:507-521`) — you are
  not touching the build rules for `wbc_plugins`; if you rename/move nothing, nothing changes.
- Don't let `wbc_interface.hpp` grow includes: it is on the exported surface
  (`CMakeLists.txt:714-727`); `pipeline_types_surface_check.cpp` will catch a leak of
  `ROBOT_MODEL`-dependent headers.
- The adapters' `Init` signatures/keys must not change (`wbc.arc_opt.*`, `wbc.inverse_dynamics.*`)
  — configs depend on them; this PR changes *selection*, not *configuration*.
- Contract-test alias pins (D2): if you touch the array types at all, the `ContactLogicInterface`
  `static_assert`s are the tripwire — the host passes contacts/wrenches straight through
  (`contract_tests.md:39`), layouts must stay identical.
- After the sweep (§5), `grep -rn "kWBCCartesian" ws/ doc/` must return zero hits;
  `grep -rn "USE_WBC" ws/src/controllers` must return only: `mit_controller_params.hpp` (the
  definition), the `declare_parameter` default line, `stage_selection.hpp` docs/`WBCTypeForBuild`,
  and historical/doc mentions updated to past tense.
