## 1. What the issue asks

Move the early/late/lost contact reconciliation FSM out of `MITController::ControlLoopCallback` into a stock `DefaultContactLogic` plugin implementing the already-ratified `ContactLogicInterface` (M1.4). Acceptance criteria:

1. Contact reconciliation no longer inline in the control loop beyond calling the plugin.
2. `DefaultContactLogic` exported and selectable via YAML `type:`.
3. Behavior matches the pre-extraction contact policy for Go2 sim defaults.
4. Host remains thin (no re-embedded FSM).

## 3. Design decisions (settled — do not re-open)

**D1 — Two-layer structure, Option B (like every other stock stage).** A plain concrete class `DefaultContactLogic : public ContactLogicInterface` holds the algorithm; a thin adapter `stock_plugins::DefaultContactLogicPlugin final : public StagePlugin<ContactLogicInterface>` in `src/plugins/contact_logic_plugins.cpp` forwards every method and builds the impl in `Init`. Mirror `src/plugins/slc_plugins.cpp` (the closest analogue: model+state, no solver).

**D2 — Files.**
- `ws/src/controllers/include/mit_controller/default_contact_logic.hpp` (exported with the other stage headers so it appears in `doc/modularity/stock_plugins.md`'s pattern; check how e.g. `swing_leg_controller.hpp` is exported and mirror).
- `ws/src/controllers/src/mit_controller/default_contact_logic.cpp`.
- `ws/src/controllers/src/plugins/contact_logic_plugins.cpp` (adapter + `PLUGINLIB_EXPORT_CLASS(stock_plugins::DefaultContactLogicPlugin, StagePlugin<ContactLogicInterface>)`).

**D3 — Parameter keys: the ratified `contact_logic.*` namespace, with a legacy bridge.** The interface (contact_logic_interface.hpp:185-187) fixes the runtime keys as `contact_logic.early_contact_detection`, `contact_logic.late_contact_detection`, `contact_logic.lost_contact_detection`, `contact_logic.late_contact_reschedule_swing_phase`. Same bridge pattern as `stage_selection.hpp`'s legacy derivation:
- The host keeps the four legacy flat declares (cpp:27-30) untouched — ULab and out-of-tree YAMLs keep working unchanged.
- The host additionally declares the four `contact_logic.*` params with **defaults taken from the legacy flat parameters** (read them first, as it already does for `gs.type`←`gait_sequencer`). An explicitly set nested key wins.
- The plugin's `Init` reads only `contact_logic.*` (via `Require<bool>` from `plugins/plugin_param_utils.hpp` — the host guarantees they're declared, so requiring is correct and fail-fast).
- `SetParameter` recognizes exactly the four `contact_logic.*` keys, returns `false` otherwise.
- Runtime changes of the legacy flat keys bridge like the `gait_sequencer` legacy branch (cpp:346-356): the param-event callback maps `early_contact_detection` → `this->set_parameter(contact_logic.early_contact_detection, v)`; the re-entered event then routes to the plugin. Comment it as inert-on-stock-path, removed by #23 (M5.4).
- Route `contact_logic.*` events to `contact_logic_->SetParameter(...)` under `wbc_lock_` (the interface mandates which lock: it's the stage's mutex, and this stage runs under `wbc_lock_`). **Branch-order caution:** insert the `contact_logic.` prefix check *before* the generic `find("gait")` / prefix branches; also note `contact_logic.type` will reach `SetParameter`, return `false`, and produce the standard "not yet supported" warning — that is the desired behavior (runtime stage swap is only implemented for the GS; keep it that way).

**D4 — Selection key and stock name.** Extend `stage_selection.hpp`:
- `inline constexpr char kContactLogicTypeKey[] = "contact_logic.type";`
- `inline constexpr char kDefaultContactLogicPlugin[] = "default_contact_logic";`
No legacy derivation function — there was never a parameter selecting a contact implementation. Host declares `contact_logic.type` with default `kDefaultContactLogicPlugin`. Update the header's doc table.

**D5 — Host wiring.** In `mit_controller_node.hpp`:
- `StageLoader<ContactLogicInterface> cl_loader_{stage_plugin_bases::kContactLogic};` — **declared in the loader block, before any `PluginPtr`** (destruction-order invariant documented at :133-137; keep it).
- `StageLoader<ContactLogicInterface>::PluginPtr contact_logic_;` — with the others. Never a `std::unique_ptr` (pluginlib deleter, M2.2 finding).
- Delete: `LegStatus`, the four toggle members, `feet_status_`, `early_contact_hold_position_`, `slip_hold_in_body_`, `last_feet_pos_targets_`.

In the constructor: load after `wbc_` (it is "the sixth stage"; there is no legacy construction order to preserve because it was never constructed): `contact_logic_ = cl_loader_.Load(stage_selection::kContactLogicTypeKey, MakeStageInit());` — unguarded like the other five (fail-fast bring-up). Add it to the "Pipeline stages loaded" INFO line.

In `ControlLoopCallback`, inside `wbc_lock_` (taken at :845), replacing :862-986:
```cpp
// Feed the contact stage, in the contract's order (contact_logic_interface.hpp).
contact_logic_->UpdateState(quad_state_temp);
contact_logic_->UpdateGaitSequence(gait_sequence_temp);
contact_logic_->UpdateWrenchSequence(wrench_sequence_temp);
contact_logic_->UpdateSwingLegState(feet_targets_temp, feet_swing_progress_temp, feet_swing_states_temp);

auto feet_targets = feet_targets_temp;
auto gait = gait_sequence_temp.contact_sequence[0];

static ContactLogicInterface::ContactEvents events;
contact_logic_->GetContactEvents(events);
for (unsigned int leg_idx = 0; leg_idx < N_LEGS; leg_idx++) {
  // ... logging + num_early_contacts as specified in §2 "stays in host"

```
Host-side event mapping (exact parity with today's messages/severities):
- `early_contact_detected[i]` → `RCLCPP_INFO "Foot [%d] has early contact"` + (if `PUBLISH_HEARTBEAT`) `num_early_contacts++`.
- `late_contact_detected[i]` → `RCLCPP_INFO "Foot [%d] has late contact"`.
- `lost_contact_detected[i]` → `RCLCPP_WARN "Foot [%d] lost contact and is kept a last contact position relative to body"`.
- `swing_scheduled_before_slc_started[i]` → the ERROR+WARN pair at :949-956. **Fidelity detail:** today both messages fire only when `feet_swing_states_temp[i] == NOT_STARTED` (the STANCE case is silent). The event covers STANCE *or* NOT_STARTED, but the host still holds `feet_swing_states_temp`, so gate the logs on `event && state == NOT_STARTED` — no interface change, byte-identical logging.
- `contact_regained[i]` → nothing (today regain is silent; the event exists for future diagnostics).

In `ModelAdaptationCallback` (:790-805): today the FSM reads the host's `quad_model_` directly; the plugin owns a clone, so add — inside the existing `wbc_lock_` section next to `wbc_->UpdateModel(quad_model_)` — `contact_logic_->UpdateModel(quad_model_);` (the interface says event-driven, only when the model changed; this is that event). Extend the "Updated used Model in WBC" pattern/log accordingly.

**D6 — Plugin internals / performance rules.** `DefaultContactLogic` members: owned `std::unique_ptr<ModelInterface> model_`, `std::unique_ptr<StateInterface> state_` (from `StageInit`, moved in `Init`); value members `GaitSequence gait_sequence_`, `WrenchSequence wrench_sequence_`, `FeetTargets feet_targets_`, `std::array<double,N_LEGS> swing_progress_`, swing-state array, the four bools, FSM state arrays, and a `ContactEvents last_events_`. Rules:
- `Update*` methods are plain member assignments (`*state_ = state;`, `gait_sequence_ = gs;` — the `*model_ = model` pattern is exactly `SwingLegController::UpdateModel`, swing_leg_controller.cpp:195). All these types are fixed-size (std::array-based) — **zero heap allocation per cycle**. Do not introduce any container that allocates in `Update*`/`Reconcile`.
- `Reconcile` = the two loops moved **verbatim** (same branch order, same conditions, same `assert` at :966), with `quad_state_temp`→`*state_`, `quad_model_`→`*model_`, member toggles, and events recorded where logs used to be. Reset `last_events_` to all-false at the top of `Reconcile`.
- `GetLegContactStates` / `GetContactEvents` are const copies of the arrays — trivially cheap.

**D7 — One deliberate, documented micro-difference.** Lines :980-981 read the **live** `quad_state_` member (unlocked, racy) instead of the cycle's `quad_state_temp` snapshot for the late/lost hold transform. The plugin necessarily uses its snapshot (`*state_`). This is a strict improvement (removes an unsynchronized read; same-cycle data, at most one 2 ms cycle fresher today by luck). Call it out in the PR changelog explicitly — it is the only intentional behavioral delta, and it is below observability in sim.

## 5. Performance (a stated requirement — prove no loss)

**Why no regression is expected (put this reasoning in the PR):**
- Per 500 Hz cycle the extraction adds ~8 virtual calls (4 `Update*`, `Reconcile`, 2 `Get*`) — the pipeline already makes dozens per cycle through the frozen stage interfaces; M2.4 measured no cost from the same pattern.
- `Update*` copies (`GaitSequence`, `WrenchSequence`, `FeetTargets`, two small arrays) are assignments into preallocated fixed-size members — no heap allocation, and the control loop already copies these same objects 1-2× per cycle today (:831-843). The added copies are KB-scale memcpys, orders of magnitude under the WBC QP solve.
- The FSM arithmetic itself is unchanged, byte for byte.
- Hard rules for the implementer: no allocation in any per-cycle path; no locks inside the plugin (the host's `wbc_lock_` is the synchronization, per the interface contract); `Reconcile` mutates state exactly once per cycle.

**Measurement protocol (mirror M2.4's proof, same scenario before/after):**
1. On `feature/modularization_central` (pre-branch), run the stock Go2 sim walk scenario; record `/wbc_solve_time` and `/solve_time` (`ros2 bag record`), plus a final `/controller_heartbeat` sample.
2. Repeat identically on the M3.1 branch.
3. Compare mean/p95 of `WBCReturn.total_time` and MPC solve time — deltas must be within run-to-run noise; `num_wbc_overtime`, `num_mpc_solver_overtime`, `num_wbc_solver_fail` must not increase. `num_early_contacts` should be in the same ballpark (it is scenario-stochastic; large deviation = behavior change, investigate).
4. Attach the numbers to the PR.
