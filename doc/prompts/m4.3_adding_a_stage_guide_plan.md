## 1. What the issue asks

Write `doc/modularity/adding_a_stage.md`: the contributor guide for adding a control stage from a
separate package. Acceptance criteria, mapped:

| AC | Where it lands |
|---|---|
| `doc/modularity/adding_a_stage.md` exists with step-by-step instructions | §4.1–§4.3 — the 7-section guide |
| Linked from main README (or controllers README) | §4.4 — main `README.md` (there is **no** `ws/src/controllers/README.md`, so "main README" is the only option) |
| References stage contracts doc and example plugin (M4.2) | Guide §1 links `stage_contracts.md`; guide §2–§4 link `example_stage_plugins` throughout |
| Mentions PR base branch `dev` | **Deliberate deviation (D1):** the guide names `feature/modularization_central`, matching actual M2–M4 practice. State the deviation and its reason explicitly in the PR description and in a closing comment on #18. |

The issue's own summary line ("copy stock plugin, export XML, set YAML `type:`, rebuild") is
**superseded by the traps comment**: "copy stock plugin" is wrong as *build* advice (the stock
wrappers' CMake wiring is not copyable out of `controllers`). The guide teaches: **stock plugin =
code template, example package = build template — different things.** This correction is the
single most important content decision; do not water it down.

## 3. Design decisions (settled with the maintainer 2026-07-29 — do not relitigate)

- **D1 — PR base wording: `feature/modularization_central`, plainly.** Chosen over the issue AC's
  `dev` (wrong today — `dev` lacks the plugin host) and over an "active integration branch"
  indirection. Consequence: the string rots when the central branch merges; mitigated by the §2
  reminder note in the PR and issue comment.
- **D2 — docs-only + two follow-up issues.** The traps comment surfaced two code-level gaps
  (`plugin_param_utils.hpp` not installed; `libX` spelling in the six stock XMLs). Do **not** fix
  them here. File them as issues (§4.6) and have the guide document *today's reality*: parameter
  reads are hand-rolled out-of-package, and the portable XML spelling is the unprefixed one (which
  the example already uses; the stock XMLs predate the rule).
- **D3 — hybrid self-containedness.** Inline in the guide: the description-XML snippet, a
  `package.xml` dependency skeleton, and the ~15-line plugin class shape. For the CMake build
  traps: short annotated excerpts **plus links to the exact lines** in
  `example_stage_plugins/CMakeLists.txt`, which stays the canonical template. Full file listings
  are *not* duplicated into the doc (drift risk); a reader who wants the complete files is sent to
  the example package explicitly.
- **D4 — validation: the implementing agent walks the guide; the human verifies evidence.** §6
  defines the walkthrough. Its transcript/evidence goes in the PR description; the human test plan
  (§6.3) is a ~15-minute verification pass, not a re-derivation.
- **D5 — the guide's section order is the traps comment's 7-section shape** ("the order you hit
  them"), ratified as-is: Pick → Write → Build → Export → Select → Test → Checklist.
- **D6 — house style.** Match the existing `doc/modularity/*.md` conventions: a
  `**Status:** … · **Applies to:** … · **Companion documents:** …` header block, `§n` internal
  references, relative links into the tree, tables where the content is tabular. Read
  `stock_plugins.md` and the example README for tone before writing.

## 4. Implementation steps

### 4.1 `doc/modularity/adding_a_stage.md` — header + sections 1–2

Header block (D6): Status "added in M4.3 (issue #18)"; companions: `stage_contracts.md`,
`plugin_lifecycle.md`, `plugin_discovery.md`, `stage_loading.md`, `stock_plugins.md`, and
`../../ws/src/examples/example_stage_plugins/README.md`. Open with the one-paragraph promise (M4's
exit criterion, same claim the example README makes): *a control stage can be added from a separate
package, selected by one YAML value, with no edit to the host.*

**§1 Pick your stage.** The frozen stage interfaces (GS / MPC / SLC / WBC / MA / ContactLogic),
each with its `StagePlugin<Interface>` base-class-type string, linking `stage_contracts.md` for the
semantic contract and `plugin_lifecycle.md` for the lifecycle. One table, no prose duplication of
the contracts doc.

**§2 Write the class.** The shape: derive `StagePlugin<Interface>`, cheap default ctor, real work
in `Init(StageInit)` (throwing `StageInitError`), forward the interface methods, one
`PLUGINLIB_EXPORT_CLASS` line. Inline the ~15-line skeleton (D3). Then the template split, stated
plainly (§1 of this plan): stock wrappers in
[`ws/src/controllers/src/plugins/`](../../ws/src/controllers/src/plugins/) are the **code**
template; [`passthrough_slc_plugin.cpp`](../../ws/src/examples/example_stage_plugins/src/passthrough_slc_plugin.cpp)
is the complete minimal worked example; the example **package** is the **build** template.
Parameter contract (from the traps comment, "two smaller items"): `Require`/`GetOr` helpers are
`controllers`-internal, so out-of-package code hand-rolls its reads (~10 lines; point at the
example's `Init`), and the contract to reproduce is: **a missing or malformed value throws
`StageInitError` naming the offending key** — never a silent fallback. `SetParameter` returns
`false` for keys the stage does not own. Reference the follow-up issue filed in §4.6 for the
helper-header install.

### 4.2 `adding_a_stage.md` — sections 3–5

**§3 Build it — the three traps, in the order you hit them.** Lift from the traps comment and the
example README §4, condensed; each trap gets: the symptom (real error text), the root cause in one
or two sentences, the fix, and *why the fix is the correct model rather than a workaround*:

1. **Never `ament_target_dependencies(<target> controllers)`** — the drake link error; take
   headers, not libraries (`target_include_directories(... SYSTEM PRIVATE
   ${controllers_INCLUDE_DIRS})`). The "why": a stage plugin references no compiled symbol of
   `controllers`/`common` — everything is pure-virtual, header-only, or plain data; the host
   supplies implementations through the vtable. Link `stock_plugins.md` §4 and
   `stage_loading.md` §6 for the in-package form of the same rule.
2. **Eigen does not come through the re-export** — the `Eigen/Geometry: No such file` error;
   `target_link_libraries(<target> Eigen3::Eigen)` (header-only; links nothing). Note this is a
   genuine gap in the `plugin_discovery.md` §1 re-export promise; do not paper over it.
3. **Mirror the host's Release flags — nothing fails if you don't.** The `-O3`(aarch64)/`-Ofast`
   block, with the consequence attached: a stage runs in the 100 Hz / 500 Hz loops; an
   under-optimised `.so` is an on-robot regression no test catches. Mention the
   `-Wno-error=maybe-uninitialized` demotion and its reason (SHARED → `-fPIC`; GCC + `-Ofast` +
   `-fPIC` Eigen false positive) so nobody "cleans it up".

Each trap excerpt links the exact `example_stage_plugins/CMakeLists.txt` lines (D3). Excerpts stay
short — the canonical, compilable text lives in the example.

**§4 Export it.** The description XML, inlined (D3) in the **portable unprefixed spelling**
(`<library path="example_slc_plugins">`-style, no `lib` prefix), with one line noting the stock
XMLs' `libX` spelling predates this rule and seeds a pluginlib warning (follow-up issue, §4.6).
Then the one discovery line — `pluginlib_export_plugin_description_file(controllers
plugins/<file>.xml)` — and why its first argument is `controllers`, not your project (it names the
ament resource the host's `StageLoader` scans, because `controllers` owns the base classes; no
allowlist to join). Link `plugin_discovery.md`. Also the library-install rule: the `.so` goes to
your package's `lib/`, because pluginlib resolves `<library path>` relative to the install prefix
of the package that owns the XML (example README §4 item 4).

**§5 Select it.** One YAML/CLI override: `-p <stage>.type:=<plugin_id>` or a params-file overlay
(reuse the example README §3 command verbatim). Fail-fast on a typo, showing the real
"names no declared plugin … declared stage plugins: …" error text — the behaviour that makes
silent fallback impossible. Runtime parameter changes via `ros2 param set` where the stage supports
them. One parenthetical: a first-class single-stage launch overlay is #19 (M4.4).

### 4.3 `adding_a_stage.md` — sections 6–7

**§6 Test it.** Test through the host's own `StageLoader` with production ament discovery (no
explicit XML path) — the same API and resource the running node uses; point at
[`test_passthrough_slc_plugin.cpp`](../../ws/src/examples/example_stage_plugins/test/test_passthrough_slc_plugin.cpp)
as the worked pattern. Note `BrickModel`/`BrickState` are `controllers`-private, so you write your
own `ModelInterface`/`StateInterface` doubles — a worked pair exists in that test file. If the
stage consumes model updates, link `model_update_broadcast.md` §3 as the model-update step (that
doc's issue map already promises this link — see §4.5).

**§7 Checklist before you PR.** A table or tick-list, each item with its consequence attached (the
traps comment is explicit that the flags item must be a checklist entry, not a code-block line):

- Release flags mirror the host (`-O3` aarch64 / `-Ofast` otherwise) — under-optimised `.so` = an
  invisible on-robot loop-timing regression.
- No link against `controllers`/`common` — headers only; the drake error means you got this wrong.
- Description XML uses the unprefixed `<library path>` spelling.
- `Init` failures throw `StageInitError` **naming the key**; `SetParameter` returns `false` for
  keys you don't own.
- No per-cycle heap allocation, no per-cycle I/O (example README §5 is the reference discipline).
- Tests load through `StageLoader` + production discovery.
- **PR base: `feature/modularization_central`** (D1).

## 5. Performance (explicitly: why there is no regression)

State these in the PR:

1. **Docs-only diff.** No source, build, XML, YAML or launch change; `git diff --stat` shows only
   `doc/` and `README.md`. Nothing that executes changed — zero runtime impact, trivially.
2. **The guide is itself a performance guard.** Its §3 trap 3 and §7 checklist are the only place
   the "plugin `.so` must match the host's optimisation flags" rule is stated for out-of-package
   contributors — the failure it prevents (silently deoptimised control-loop stage) is invisible
   to every automated test. Landing this doc *reduces* the long-term risk of on-robot performance
   regressions from third-party stages.
3. **The walkthrough scratch package is deleted, not shipped** (§6.1); it never enters the tree or
   any install.

## 6. Validation (D4: the agent walks, the human verifies)

### 6.1 Agent walkthrough (mandatory, during development — before the PR is opened)

Follow **your own guide, verbatim, as written** — not your memory of the example package. Any
point where you must consult something the guide doesn't say or link is a guide bug: fix the guide
and note it in the PR ("walkthrough findings"). Steps:

1. Create a fresh scratch package `ws/src/walkthrough_slc/` (name it so it obviously isn't the
   example) implementing a minimal SLC stage under a **new** plugin id (e.g. `walkthrough_slc`),
   written by following guide §1–§4 only. Do **not** copy `example_stage_plugins` wholesale — the
   point is that the guide's steps suffice; consult the example only where the guide links it.
2. Build it in Docker (command in §0) — must compile clean under the mirrored Release flags.
3. Negative checks (these prove the traps text is accurate): temporarily switch the CMake to
   `ament_target_dependencies(... controllers ...)` and confirm the drake error appears as the
   guide quotes it; revert. Drop `Eigen3::Eigen` and confirm the `Eigen/Geometry` error; revert.
4. Guide §5: launch the Go2 sim (README "Quick start (simulation)") with
   `-p slc.type:=walkthrough_slc`. Gate: clean bring-up, plugin loaded, robot stands. Then misspell
   the id and confirm the fail-fast error names the declared plugins (including yours — which also
   proves discovery worked).
5. Delete `ws/src/walkthrough_slc/` and rebuild/`git status` to confirm the tree is clean.
6. Record in the PR description: the walkthrough package's file list + key snippets, the build
   command and result, the sim bring-up log lines showing the load and the fail-fast message, and
   any guide fixes the walkthrough forced.

### 6.2 Automated checks

- Docs-only: no colcon test cycle is *required* by the diff; still run
  `colcon build --packages-up-to controllers example_stage_plugins` once at the end in Docker to
  prove the tree you're PRing from is green (guards against accidental stray edits).
- Link check: every relative link in `adding_a_stage.md`, the README additions, and the §4.5
  rewords resolves (`grep -o` the paths and test existence, or use whatever link checker is at
  hand). Every `§n` cross-reference in the guide points at a section that exists.
- Every quoted error message in the guide is byte-accurate to what the walkthrough actually
  produced (paste from the walkthrough logs, don't retype).

### 6.3 Human test plan (put this, expanded, in the PR — ~15 minutes)

1. **Prose pass** (5 min): read `adding_a_stage.md` top to bottom. Gate: the 7 sections are in the
   stated order; the stock-plugin-vs-example-package template split is stated plainly; each of the
   three traps has symptom + cause + fix + why; the §7 checklist carries consequences, not bare
   imperatives; PR base is named as `feature/modularization_central`.
2. **Evidence pass** (5 min): check the PR description contains the §6.1 walkthrough evidence —
   build output, sim bring-up log with the plugin load line, the fail-fast error listing the
   scratch plugin id, and the negative-check error texts matching the guide's quotes.
3. **Spot-check pass** (5 min): follow three links at random from the guide into
   `example_stage_plugins` / `doc/modularity` and confirm they land on the claimed content; click
   the README links; confirm `git diff --stat` touches only `doc/` and `README.md`; confirm the
   two follow-up issues (§4.6) exist and are referenced from the guide.
4. **Optional deep gate** (only if desired): repeat §6.1 yourself end-to-end (~45–60 min).
